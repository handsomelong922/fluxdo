# 修复 CDK 返回帖子后 429 限流

## Goal

消除用户从帖子进入 `https://cdk.linux.do/` 或 `https://credit.linux.do/` 完成领取或支付、再返回帖子并刷新时稳定触发的 HTTP 429，恢复连续浏览体验，同时保留服务端真实限流保护和现有外部站点业务流程。

## Confirmed Facts

- 正常浏览帖子不会频繁触发“等会儿再重试”限制。
- 帖子中的 CDK 链接会打开 `https://cdk.linux.do/`，部分领取流程会继续进入 `https://credit.linux.do/`。
- CDK 与 credit 均为本项目认可的官方站点，不应被当作不可信跳转而阻断。
- 用户在领取或支付完成后返回原帖子，再刷新时基本 100% 收到 429，帖子无法刷新，只能等待限流窗口结束。
- 用户已明确要求完成根因排查、修复、充分验证、本地独立提交，并在整批工作完成后推送 GitHub。
- 代码证据显示，`TopicDetailPage` 在子路由返回时会因 `_topicChannelNeedsCatchUp` 被无条件置为 `true`，自动调用 `refreshWithPostNumber()`；用户随后手动刷新会形成连续的帖子详情请求。
- 代码证据显示，`CdkPage` 打开时的 `_seedSessionAndReloadIfNeeded()` 会静默调用 `CdkOAuthService.authorizeSilently()`；该路径由 2026-07-08 的“speed up cdk page”提交重新引入，而 2026-06-09 的既有任务已将其识别为不应存在的自动请求路径。
- `credit.linux.do` 走通用 `WebViewPage`，不执行 CDK 静默 OAuth，但仍会触发子路由返回时的无条件帖子刷新；`cdk.linux.do` 同时命中两条路径。

## Requirements

- 追踪帖子链接点击、官方站点承载方式、登录态或 Cookie 同步、页面返回、帖子恢复和刷新请求的完整数据流。
- 用代码、日志、测试或可控复现确定触发 429 的具体客户端行为，不以推测代替根因证据。
- 修复导致请求突发、重复请求、错误重试、错误恢复刷新或认证状态异常的根因。
- 不得通过吞掉 429、无限延迟刷新、关闭合法刷新或绕过服务端限流来掩盖问题。
- 保持普通帖子浏览、普通外链、CDK 领取、credit 支付、WebView/浏览器返回以及帖子刷新行为兼容。
- 为根因补充足以防止复发的自动化回归测试；无法完全自动化的设备交互必须有可重复的定向验证证据。
- 仅提交本任务产生的文件或 hunk，不混入当前工作区已有的未跟踪或未提交内容。
- 不再使用虚拟机或“持续模拟真实浏览”作为本任务的验收前提；以静态代码证据、单元测试、定向静态分析和可执行的本地 smoke 检查为主。

## Acceptance Criteria

- [x] 返回后首次帖子刷新能够按正常单次刷新语义执行；服务端真实返回 429 时仍沿用明确且有限的错误处理。
- [x] 普通帖子刷新、普通外链返回、CDK/credit 链接识别和领取/支付页面导航没有行为回归。
- [x] 相关测试、静态分析与可执行的 smoke 验证全部通过，并如实记录无法执行的设备级验证及其影响。
- [ ] 变更按独立 bug 修复形成一个本地提交，确认提交内容后推送到当前 GitHub 远端分支。

## Out of Scope

- 修改 `cdk.linux.do`、`credit.linux.do` 或 Discourse 服务端的限流策略，除非客户端证据证明必须配套修改且仓库内存在对应服务端代码。
- 放宽所有 API 的 429 处理或改变与本问题无关的网络请求节流策略。
- 借机重构无关的帖子详情、WebView 或网络层代码。
